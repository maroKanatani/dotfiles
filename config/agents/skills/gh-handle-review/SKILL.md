# GitHubレビューを扱う

## レビューする

1. 対象の差分、リポジトリ固有の指示、関連する実装とテストを確認する。
2. 事実と影響を示し、相手を責めず対等な立場でコメントする。
3. prefixは指摘ごとに次を上から問い、最初にYesとなったものを使う。深刻度や分類ラベルから機械的に変換しない。
   - この指摘が未対応のままならApproveしないか → `must:`
   - 実装の意図や背景を作者に尋ねたいか → `q:`
   - 将来対応したいが、現在のPRでは不要か → `nr:`
   - 対応しなくてよい些細な指摘か → `nits:`
   - 対応を求めない参考情報か → `fyi:`
   - 上記以外の見解や提案 → `imo:`

   `must:`は原則2件以内とする。3件以上になる場合はPR全体の設計に問題がある可能性を疑い、個別コメントではなくレビュー本文へ構造的な指摘としてまとめる。
4. 1コメントは2段落以内とし、1段落目に問題と影響、2段落目に修正案を書く。2段落へ収まらない場合は複数の指摘が混ざっているため分割する。挨拶、称賛、一般論、同じ内容の言い換えを足さない。
5. 根拠は`file:line`で示し、そこを読めば分かるコードは再掲しない。コードブロックやMermaid図は、文章だけより意図が明確になる場合だけ添える。
6. 次のものは書かない。いずれもレビューを受ける側が行動に移せない。
   - 検討したうえで指摘しなかった事項、確認して問題がなかった観点の一覧
   - 深刻度の集計、検証の経緯、レビュー体制の説明
7. 投稿コマンドを実行する前に、手順3から6を満たすかを数えて確認する。利用者へ修正が必要な件数を報告済みなら、`must:`の件数と一致することも確認する。超えていれば投稿せずに直す。

例:

```text
must: `items`が空のとき`items[0]`で例外になります。先頭要素へアクセスする前に空判定を追加してください。

nits: `deadline`は再試行回数を保持しているので、`retryCount`の方が読み取りやすそうです。

nr: 境界値のテストが未追加ですが、このPRでは対応不要です。追跡Issueを作って別PRで追加しませんか。
```

## AIレビュー結果を共有する

- AI出力に認証情報、秘密値、個人情報、公開できない情報がないことを確認する。含まれる場合は投稿せず、利用者へ報告する。
- 安全に共有できる場合は出力を改変せず、次の形式へ収める。`details`の本文は手順4と手順6の対象外とする。

```html
<details><summary>AIレビューの指摘</summary>

（AIの出力をそのまま貼る）

</details>
```

## レビュー指摘へ対応する

1. 指摘、関連する会話、現在の実装、PR本文、実装内のコードコメントを確認する。
2. 指摘の契機ではなく、観測できる問題の根本原因を修正する。
3. 変更箇所に近い検証を実行し、必要に応じて利用箇所まで広げる。
4. コミットする場合はConventional Commits形式で具体的な変更内容を書く。`fix: レビュー指摘に対応`のように作業の契機だけを書かない。
5. push前に差分、branch、remoteを確認する。pushが依頼範囲に含まれない場合は実行しない。
6. push後に最新の実装とPR本文および実装内のコードコメントを照合し、依頼範囲内の乖離を修正する。
7. レビューへの返信やthreadのresolveは、利用者の依頼またはリポジトリ固有の運用に含まれる場合だけ行う。
