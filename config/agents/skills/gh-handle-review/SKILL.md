# GitHubレビューを扱う

## レビューする

1. 対象の差分、リポジトリ固有の指示、関連する実装とテストを確認する。
2. 事実と影響を示し、相手を責めず対等な立場でコメントする。
3. 意図に合うprefixを付ける。
   - `must:` 現在のPRで修正が必要。未対応ならApproveしない
   - `imo:` 個人的な見解や提案。修正または議論を検討する
   - `nr:` 現在のPRでは対応不要だが、将来対応したい提案。タスク化または別PRを検討する
   - `nits:` 無視してよい些細な指摘。対応不要
   - `fyi:` 参考情報。対応不要
   - `q:` 質問や意図の確認。
4. 1項目を原則1〜2行に収め、問題、影響、必要な対応を過不足なく書く。挨拶、称賛、一般論、同じ内容の言い換えを足さない。
5. コードブロックやMermaid図は、文章だけより意図が明確になる場合だけ添える。

例:

```text
must: `items`が空のとき`items[0]`で例外になります。先頭要素へアクセスする前に空判定を追加してください。

nits: `deadline`は再試行回数を保持しているので、`retryCount`の方が読み取りやすそうです。

nr: 境界値のテストが未追加ですが、このPRでは対応不要です。追跡Issueを作って別PRで追加しませんか。
```

## AIレビュー結果を共有する

- AI出力に認証情報、秘密値、個人情報、公開できない情報がないことを確認する。含まれる場合は投稿せず、利用者へ報告する。
- 安全に共有できる場合は出力を改変せず、次の形式へ収める。`details`の本文は1〜2行の制限対象外とする。

```html
<details><summary>AIレビューの指摘</summary>

（AIの出力をそのまま貼る）

</details>
```

## レビュー指摘へ対応する

1. 指摘、関連する会話、現在の実装、PR本文、実装内のコードコメントを確認する。
2. 指摘の契機ではなく、観測できる問題の根本原因を修正する。
3. 変更箇所に近い検証を実行し、必要に応じて利用箇所まで広げる。
4. コミットする場合はConventional Commits形式で具体的な変更内容を書く。`fix: レビュー指摘に対応`のように作業の契機だけを書かない。
5. push前に差分、branch、remoteを確認する。pushが依頼範囲に含まれない場合は実行しない。
6. push後に最新の実装とPR本文および実装内のコードコメントを照合し、依頼範囲内の乖離を修正する。
7. レビューへの返信やthreadのresolveは、利用者の依頼またはリポジトリ固有の運用に含まれる場合だけ行う。
